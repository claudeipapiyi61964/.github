<p>评测最容易犯的错，是用一次登录成功与否来判断一条池子好不好。登录、订阅、接口调用这三个场景对出口的要求完全不同：登录看的是行为一致性，订阅看的是页面与支付的完整链路，接口看的是成功率与长尾延迟。用同一套方法测三件事，结论一定偏。这篇给一套可以照着执行的对照测法，包括样本量、观察指标和判定线。</p>

<h2>一、先定基线和样本量，否则数据没法比</h2>
<p>没有基线的测试只能叫体验，不能叫评测。基线的作用是回答"这个数字算好还是算差"。</p>
<h3>基线用本地网络跑同一组请求</h3>
<p>在不用代理的情况下，用同样的脚本、同样的目标、同样的时间段跑一遍，得到一组参照值。后面所有代理的测试结果都和这组比。差异大的地方才是需要解释的地方，绝对值本身意义有限。</p>
<h3>每个场景至少 30 个样本</h3>
<p>低于 30 个样本，一次偶发失败就能让成功率跳动 3 个百分点以上，结论不可靠。登录场景可以少一些，20 次够用；接口场景建议 100 次以上，因为要看长尾。</p>

<h2>二、登录场景：测的是验证页出现的频率</h2>
<p>登录成功不等于通过。真正要统计的是"需要额外验证"的比例，以及验证的强度。</p>
<h3>记录三档结果，不要只记成功失败</h3>
<p>直接进入、需要邮箱或短信验证、被拒绝。三档分开记，才能看出出口是"完全不能用"还是"偶尔触发验证"。后者在换一条线之后往往就消失了，前者说明地址段本身有问题。</p>
<h3>同一账号不要跨线混测</h3>
<p>一个账号在十条线上各登一次，测出来的数据没法归因。正确做法是一个账号固定一条线，测 20 次；换线时换账号。账号和出口要成对出现，这是对照实验的基本要求。</p>

<h2>三、订阅与支付环节：测的是页面完整加载</h2>
<p>这个环节的失败常常不是被拒绝，而是页面加载到一半卡住。只测登录页能打开是不够的。</p>

<h3>要走到支付方式选择页为止</h3>
<p>把流程拆成四步：进入定价页、选择方案、进入结算页、出现支付方式。每一步记录耗时和是否完整渲染。卡在第三步最常见，表现是页面空白或一直转圈，而 HTTP 状态码是 200，用状态码判断会漏掉这类失败。</p>
<h3>静态资源也要走同一条出口</h3>
<p>如果只有接口走代理、静态资源走本地，页面会出现"文字出来了但样式没出来"的情况，看起来像目标站点的问题。测试前确认浏览器或客户端的全部流量都走同一出口。</p>

<h2>四、接口调用：测的是成功率和长尾延迟</h2>
<p>接口场景最容易被平均值骗。平均 800 毫秒听起来不错，如果 P95 是 8 秒，实际体验就是每隔一会儿卡一次。</p>
<h3>看 P50、P95 和失败分布</h3>
<p>三个数一起看：P50 反映常态，P95 反映糟糕时刻，失败分布反映稳定性。只报平均值等于隐藏了最需要修的部分。用脚本记录每次耗时，排序后取分位值，不要用眼睛估。</p>
<h3>并发要分档加，不要一次打满</h3>
<p>从 1 并发开始，依次加到 5、10、20，每档跑 100 次。观察延迟在哪一档开始抬升，那个点就是这条池的实际可用并发。宣传的并发上限通常高于这个拐点。</p>

<h2>五、三组数据怎么放在一起判断</h2>
<p>三个场景的结论经常不一致：登录表现好、接口表现差，或者反过来。这时候不要取平均分，要看业务权重。</p>

<h2>常见问答</h2>
<h3>测试需要单独准备账号吗？</h3>
<p>答：需要，而且不要用主力账号做压力测试。测试账号也要有完整的使用痕迹，否则测出来的高失败率可能来自账号本身太新，而不是出口的问题。</p>
<h3>同一个池在不同时间测，结果差很多正常吗？</h3>
<p>答：正常。住宅线路的负载随当地作息变化，晚高峰普遍更差。评测结论必须标注测试时间段，否则无法复现。</p>
<h3>要不要测不同地区的出口？</h3>
<p>答：如果业务只用一个地区，先把这个地区测透。多地区横评的成本很高，容易做成"每个地区都测了一点、每个都不够深"。</p>
<h3>测试脚本用什么写比较省事？</h3>
<p>答：能用现成的 HTTP 客户端就别自己造。关键是记录结构化日志（时间、出口、目标、耗时、结果），后面用一张表汇总即可，工具本身不重要。</p>

<h2>合规提示</h2>
<p>评测应在获得授权的账号与资源上进行，遵守服务商条款及目标平台的服务协议，测试频率应控制在合理范围。</p>
<p>测试产生的日志可能包含账号标识与访问记录，应按最小必要原则保存并限制访问。</p>
